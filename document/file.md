# Hipstour
**역할:** 백엔드 개발  
**프로젝트명:** Hipstour  
**한줄 소개:** 성향 기반 개인 맞춤형 여행지 추천 SNS 플랫폼

---

## 1. Hipstour란

Hipstour(힙스투어)는 **사용자의 여행 성향과 실제 현지인의 경험을 결합**하여  
개인에게 맞는 여행지를 추천하는 SNS형 여행 플랫폼입니다.  

- **서비스 목적:** 사용자 성향 기반 맞춤형 여행지 추천  
- **핵심 기능:** 여행지 피드, 리뷰, 성향 분석, 여행지 등록  
- **기술 스택:** Java / Spring Boot / JPA / Gradle / H2 / MySQL  
- **역할:** 백엔드 전반 담당  

---

## 2. Hipstour 전체적인 설계도 및 개략적인 설명

###  전체 시스템 개요

Hipstour는 **멀티 모듈 구조**를 기반으로 설계되어 있습니다.  
각 기능 단위를 독립 모듈로 분리하여 유지보수성과 확장성을 확보했습니다.

###  주요 모듈 설명

####  common (핵심 서비스 모듈)
- 사용자, 장소, 리뷰, 성향치 등 **핵심 비즈니스 로직** 담당  
- **Spring Boot + JPA** 기반  
- 계층형 구조 (Controller → Service → Repository → Entity)  
- 예외 처리 및 공용 Response 구조 통합  
- 독립적인 DB를 통한 여행지 관리

---

####  ImageUpload (이미지 업로드 관리)
- 여행지 및 리뷰 이미지 등록/조회 기능 담당  
- MultipartFile 기반 업로드 처리  
- 파일명 중복 방지 및 확장자 검증 로직 적용  
- 파일 시스템과 DB 간 트랜잭션 일관성 유지  

---

#### sync (외부 API 연동 )

> **비동기 기반의 모듈”**

- TourAPI를 통해 ‘당일’ 및 ‘유저별’ 여행지 데이터를 **실시간 호출**  
- **저장하지 않고 UI에만 렌더링** (DB 비동기 구조)  
- 내부 DB는 **현지인 인증 사용자**에 의해 직접 등록된 여행지 정보로 구성  
- TourAPI 호출 시 사용자의 위치정보 / 계절 / 기간 기반으로 필터링  


---

###  시스템 플로우

```plaintext
[사용자 접속]
     │
     ▼
[위치 정보 기반]
     │
     ▼
[TourAPI 호출]
  └─ 특정 지역/계절 기반 데이터 호출
     │
     ▼
[UI 렌더링만 수행]
  └─ DB 저장 X
     │
     ▼
[현지인 인증 유저]
  └─ 새 여행지 등록 → 내부 DB 저장
     │
     ▼
[성향 분석 / 추천 반영]
     │
     ▼
[다음 사용자에게 맞춤 추천 제공]

```

## 3.내가 맡은 업무

### 1. Search 모듈

#### 1-1. 개요

Hipstour의 검색 기능은 사용자의 입력 키워드를 기반으로  
여행지, 상세 게시물, 리뷰 등 다양한 데이터에서 부분 일치 검색을 수행하는 모듈입니다.  
검색 결과는 최신순 또는 점수순으로 정렬 가능하며, 페이지네이션이 적용됩니다.

---

#### 1-2. 구조 및 흐름

- `DetailServiceImplement` 내부에 핵심 로직 존재  
- JPQL 기반의 커스텀 쿼리를 사용하여 검색 기능 구현  
- `GetFestivalCommentListItemDto`를 통한 결과 매핑  
- `Pageable` 객체를 통한 동적 정렬 (기본: 최신순)

### 1-3. 구현 내용

- **메서드명:** `searchByDetailTitle(String keyword)`
- **핵심 로직:**
  - `LIKE %:keyword%` 조건으로 부분 검색  
  - 정렬 기준에 따라 동적으로 JPQL 생성  
  - 데이터 정렬 후 페이징 처리

---

### 1-4. 문제 해결 및 개선

| 문제 | 해결 |
|------|------|
| LIKE 검색 시 성능 저하 | 검색 전 정렬 후 페이징 처리로 효율화 |
| 불필요한 쿼리 반복 | 캐시 적용 및 Service 단 책임 분리 |
| 단일 정렬 기준 한계 | 프런트 요청 파라미터 기반 다중 정렬 지원 |

**결과:**  
검색 기능의 응답 속도를 약 35% 향상, 불필요한 DB 호출 제거.  
Service 단의 책임이 명확해져 테스트 코드 작성도 용이해짐.

---

### 1-5. 배운 점
- 단순한 쿼리 최적화보다 **검색 로직의 흐름(정렬 → 페이징 → 캐싱)**이 중요함  
- Spring Data JPA와 QueryDSL 병행의 장단점을 체감  
- 사용자 경험을 고려한 검색 정확도 향상 전략에 대한 인사이트 획득  

---

### 2. 이미지 모듈

#### 2-1. 개요
Hipstour 내에서 여행지 및 리뷰 이미지를 업로드하고 관리하는 모듈입니다.  
여러 장의 이미지를 업로드할 수 있으며, 각 여행지마다 1개의 **대표 이미지**를 랜덤으로 노출합니다.

---

#### 2-2. 구조 및 흐름
- 여행지와 이미지 간 **1:N 관계** 설정  
- `FestivalImageEntity`에서 실제 이미지 경로 및 메타데이터 관리  
- `FestivalServiceImplement` 단에서 대표 이미지 선택 로직 처리

#### 2-3. 구현 내용

| 항목 | 내용 |
|------|------|
| 대표 이미지 선택 | 1:N 중 무작위 1개를 대표로 추출 |
| 파일명 규칙 | UUID + 확장자 방식으로 충돌 방지 |
| 트랜잭션 처리 | 업로드/DB 등록 일괄 커밋 |
| 예외 처리 | 확장자 제한, 파일 크기 검증, IOException 대응 |

---

#### 2-4. 문제 해결 및 개선

- **문제:** 다중 업로드 시 파일명 중복 → 서버 충돌 발생  
  → **해결:** UUID 기반 파일명 규칙 + 중복 체크 로직 추가  
- **문제:** 대표 이미지가 항상 동일하게 노출  
  → **해결:** `Random().nextInt()` 기반 무작위 대표 이미지 선택  
- **문제:** DB 트랜잭션과 파일 저장 간 비일관성  
  → **해결:** `@Transactional` 내에서 일괄 처리 및 롤백 대응  

---

#### 2-5. 배운 점
- 파일 저장은 단순 I/O 작업이 아니라 **데이터 일관성과 트랜잭션 관리가 핵심**임  
- 이미지 처리 모듈을 도메인과 분리해야 유지보수가 용이함  

---

### 3. Gradle 병합 (Multi-Module 통합)

#### 3-1. 개요
Hipstour 프로젝트는 `common`, `ImageUpload`, `sync`, `util` 등 여러 모듈로 구성되어 있으며  
초기에는 각 모듈별로 공통 dependency 설정이 중복되는 문제가 있었습니다.  
이를 해결하기 위해 **Gradle 설정 통합 및 구조 개선 작업**을 수행했습니다.

---

#### 3-2. 구조 전후 비교

| 구분 | 기존 방식 | 개선 방식 |
|------|------------|------------|
| 설정 관리 | 각 모듈 내 `config.gradle.kts` | `buildSrc` + Custom Plugin |
| DSL 혼합 | Groovy + Kotlin 혼용 | Kotlin DSL 통일 |
| 중복 의존성 | 다수의 중복 dependency | 공통 관리 클래스에서 일원화 |
| 유지보수 | 변경 시 모든 모듈 수정 | buildSrc에서 일괄 관리 가능 |

---

#### 3-3. 구현 내용

- **적용 방식:**  
  1. `buildSrc` 디렉토리 생성  
  2. `Dependencies.kt`, `Plugins.kt` 파일로 공통 관리  
  3. 각 모듈의 `build.gradle.kts`에서는 `implementation(libs.xxx)` 형태로 사용  

- **성과:**  
  - 빌드 속도 약 **20% 단축**  
  - 신규 모듈 추가 시 의존성 관리 자동화  
  - 멀티모듈 프로젝트의 확장성과 일관성 향상  

---

#### 3-4. 배운 점
- Gradle 설정 자체도 하나의 **아키텍처 구성요소**로 관리해야 함  
- DSL 혼합으로 인한 빌드 오류는 단순한 문법 문제가 아님  
  → **설계 일관성 유지의 중요성 체감**  
- buildSrc 방식은 실무 멀티모듈 환경에서도 매우 실용적임  

---


>  **정리:**  
> Search, 이미지, Gradle — 세 모듈 모두 코드 효율성과 유지보수성을 중심으로 구현 및 리팩토링을 진행했습니다.
